# 学習ログ発信パイプライン 設計

作成: 2026-07-21 / ステータス: 設計（CEOレビュー待ち）

## 目的

宅建の学習と開発の日々を、姜さんの手間をほぼ増やさずに「発信の素材」に変える。最終目的は、顧客・商談先に「AIでここまで自分でやってる人だ」と見せて信頼を作ること。副次的に、建設・不動産業界内で広く信用を積む。

**複利の原則**: 一度作る仕組みが、宅建だけでなく施工管理技士アプリ・将来の別プロダクトの発信にも使い回せること。1回の発信が消えず、合格時の総まとめ記事へ束なり、商談で反復利用されること。

## 姜さんの手順（毎日やること・これだけ）

1. **アプリで勉強し、問題ごとにメモを書く**（今まで通り）
2. **その日の終わりに「今日の学習を書き出す」を押し**、出た内容を `takken-drill/docs/study-log/YYYY-MM-DD.md` に保存
3. **Claude Codeに「今日の発信素材を作って」と言う**（私がgitログ＋メモを読んでX用/Note用を生成）
4. **出てきた素材を確認し、OKなら cowork に「これ投稿して」と渡す**（Noteは手貼り／Xはcoworkが投稿）

※ 実質の手作業は 1（勉強のついで）と 2（保存1回）だけ。3・4は指示するだけ。

## 役割分担（データにアクセスできる者が担う）

| 担い手 | 役割 | 根拠 |
|---|---|---|
| **アプリ（takken-drill）** | 学習メモに日時を刻む＋当日分をファイルに書き出す | Firestore内のメモを外に出す橋 |
| **このClaude Code** | gitログ＋書き出しメモを読み、X用/Note用の素材ファイルを生成 | ローカルのgit・AI-HQの正史（ブランド文脈）を読める |
| **Claude Code cowork** | 生成された素材ファイルを見てX・Noteに実際に投稿 | ブラウザ操作ができる |
| **姜さん** | 学習メモを書く／最終的な投稿可否の判断 | ネタ出し＋レビュー＋投稿判断のみ（メモリー準拠） |

誰もFirestoreに危険な介入をしない。データはリポジトリのファイルとして流れる。

## 媒体判断

- **X**: 日々の観察者投稿（"AIが運用中"と明示）。coworkがブラウザ投稿するのでX APIの有料プラン・認証情報管理は不要。
- **Note**: 合格時の総まとめ1本（商談で見せるURL）。**公式投稿APIが2026年時点で存在せず、非公式APIはブランド毀損・凍結リスクがあるため使わない**（複数の実装者が「本気のアカウントでは避けるべき」と結論。出典: note.com/kawayasblog等）。coworkが手貼り、または下書き保存まで。
- 完全自動投稿は追わない。「素材が毎日ファイルに溜まり、姜さんは投稿判断だけ」までを自動化の到達点とする。

## A. アプリ改修（takken-drill）

### A-1. メモに日時を刻む

**現状**: `notes: Record<string, string>`（問題ID → 本文）。上書きのみで日時が残らない。型は `src/App.tsx`（ProgressState L48-53）と `src/firebase.ts`（SyncedProgress L239-244、mergeSyncedProgress L270-276）の両方にある。

**変更後**: `notes: Record<string, { text: string; updatedAt: string }>`。saveNote が保存時に `new Date().toISOString()` を刻む。

**後方互換（必須）**: 既存メモは古い `string` 形式でFirestore/localStorageに存在する。読み込み時に「文字列なら `{ text: 文字列, updatedAt: "" }` に変換」する移行を、localStorage読込・Firestore同期の両経路に入れる。これがないと既存メモが壊れる。

**端末間マージ**: `mergeSyncedProgress` の notes マージを、`updatedAt` が新しい方を採る方式にする（既存の answers が `answeredAt` で採るのと同じ思想）。updatedAt が空（旧データ）同士は非空を優先。

**UIは不変**: 姜さんのメモ入力体験は変えない。裏で日時が付くだけ。

### A-2. 当日の学習ログを書き出す

**機能**: 「今日の学習を書き出す」操作で、当日 `updatedAt` のメモを Markdown テキストに整形して出力する。

**出力形式**（クリップボードコピー、またはファイルダウンロード `takken-drill-studylog-YYYY-MM-DD.md`）:

```markdown
# 学習ログ 2026-07-21

## 抵当権（令和4年 問6）
（メモ本文）

## 都市計画法（令和3年12月 問15）
（メモ本文）
```

- 「当日分」の判定は端末ローカル日付（既存 `localDateKey` を使う）。
- 姜さんはこの出力を `takken-drill/docs/study-log/2026-07-21.md` に保存する（またはコピーして貼る）。この一手間だけが手動。将来はここも自動化余地あり（今はやらない）。

### A-3. テスト（TDDのRED→GREEN）

1. 新規メモ保存で `updatedAt` が刻まれる
2. 旧 `string` 形式メモが読込時に `{ text, updatedAt: "" }` に移行される
3. 端末間マージで `updatedAt` の新しいメモが勝つ
4. 書き出しが、当日 `updatedAt` のメモだけを拾い、他日を除外する
5. 書き出しMarkdownが問題見出し＋本文の形式になる

**テスト基盤**: 現状 vitest 等が無いので、`vitest` を devDependency に追加し、純粋関数（移行・マージ・書き出し整形）をUIから切り出して単体テストする。UIコンポーネントのテストは今回のスコープ外。

## B. 発信スキル（AI-HQ）

### B-1. スキルの位置づけ

AI-HQに新スキルを作る。宅建専用にしない——「任意のリポジトリの gitログ ＋ 日付つき学習ログ を読んで、X用/Note用の発信素材を生成する」汎用装置。施工管理技士アプリ・将来プロダクトで再利用できる（複利）。

### B-2. 入力

- 対象リポジトリの `git log`（指定日 or 直近N日のコミット。開発の進捗＝バグ修正・新機能）
- `docs/study-log/YYYY-MM-DD.md`（当日の学習ログ。A-2の出力）
- AI-HQの正史（brand-intelligence＝TechBullらしさ、署名経済の発信方針、過去の発信ログ＝重複回避）

### B-3. 出力

指定日について2ファイルを生成:

- `AI-HQ/outputs/broadcast/YYYY-MM-DD-x.md` — X用の短い観察者投稿（複数案）。"AIが運用しています"の明示を含む。第三者観察視点（「この開発者は今日…」）。
- `AI-HQ/outputs/broadcast/YYYY-MM-DD-note.md` — Note用の下書き段落（総まとめ記事に後で束ねる素材）。

**トーン規律**: 観察者視点／AI運用明示／技術自慢にしない（非エンジニアにも伝わる温度）／建設系発信の炎上防止3型を守る（メモリー準拠）。

### B-4. レビューゲート

生成物は外部に出るドラフト。編集長レビュアーを通し、姜さんの投稿判断を待つ（YOU MUST: 外部に出るものは勝手に実行せず必ずドラフトを見せる）。

## C. 発信ログ（セッションをまたぐ継続）

`AI-HQ/outputs/broadcast/broadcast-log.md` に「いつ・どの媒体に・何を発信したか（or 発信予定か）」を1行ずつ残す。

- 効果1: 記憶のない別セッションのClaude Codeが、これを読めば「昨日まで何を発信したか」がわかり、重複せず続きを書ける（＝自動化の代替。launchd不要）。
- 効果2: 合格時、全ログとNote素材を束ねて「自作アプリで宅建に合格してみた」総まとめ記事を生成する材料になる。
- coworkはこのログと素材ファイルを見て投稿し、投稿後のURLをログに書き戻す。

## スコープ外（今はやらない・YAGNI）

- 毎朝launchd自動起動（Cの発信ログで代替。Claude Codeを開いた時に続きから作れる）
- X APIによる自動投稿（coworkのブラウザ投稿で足りる）
- Note非公式API（ブランドリスクで不採用）
- アプリのメモ書き出しの完全自動化（当面は姜さんがファイル保存する一手間を許容）
- 施工管理技士アプリへの適用（宅建で型ができてから流用）
